# Tinium APK signing setup (Windows 11)

This implements persistent development signing and permanent beta/production signing.
It does **not** implement an updater or publish GitHub Releases. Review and merge the
signing pull request before running these workflows on `main`.

## What changed and why

- **Build Tinium Development APK** (`build-apk.yml`) still uses Java 21, the same
  SDK/Gradle setup, and `:app:assembleArm64GmsDebug --stacktrace --no-daemon`.
  It restores `DEBUG_KEYSTORE_BASE64` to `$HOME/.android/debug.keystore`, validates
  its private-key alias and passwords, and uploads the existing APK artifact.
- Trusted `main` builds in `build.yml` use that same debug secret. Pull-request
  workflows use disposable debug keys and have no secret bindings. PR artifacts
  are for CI inspection, not for installing successive development updates.
- **Beta Release Build** and **Production Release Build** are manual, `main`-only
  workflows. Both restore the same release secret outside the checkout, sign with
  Gradle, verify each APK against that keystore's certificate, and upload private
  Actions artifacts and the existing changelog. No release tags or public GitHub
  Releases are created. Artifacts remain accessible according to repository access.
- Gradle never falls back to debug signing for a release. Missing release
  credentials fail packaging clearly, while debug builds and IDE sync still work.
- The legacy nightly and Telegram jobs are explicitly paused. They check out the
  separate `beta` branch and use older signing/distribution paths; migrating or
  enabling that distribution is a separate task. No Telegram messages are sent.
- Restored keystores have restrictive file permissions and are removed in an
  `always()` workflow step. Failed decoding/validation removes its temporary file.
  No signing keys are generated by development or release distribution workflows.
  Only secret-free PR CI creates disposable debug keys.

### Previous release failure

`ilharp/sign-android-release@v2.0.0` accepts `signingKey` as a **Base64-encoded
binary keystore** and otherwise looks for `ANDROID_SIGNING_KEY`. Both old release
workflows supplied `secrets.KEYSTORE`, with `KEY_ALIAS`, `KEYSTORE_PASSWORD`, and
`KEY_PASSWORD`. An absent `KEYSTORE` and absent fallback `ANDROID_SIGNING_KEY`
explain `Cannot find signingKey/ANDROID_SIGNING_KEY`. That was a missing/mismatched
secret, not a Kotlin compilation error. The new workflows use the requested
`ANDROID_*` names directly and validate them before building; no second signing
action or debug-signed intermediate release is needed.

**If you already have a release keystore or previously configured `KEYSTORE`,
recover and reuse that exact identity.** Rename/copy its secret values to the new
names after verifying the certificate fingerprint. Do not generate a replacement
for an application already distributed with a permanent release key.

## 1. Install Java and choose a secure folder

Install the Windows x64 **JDK 21** from [Eclipse Temurin](https://adoptium.net/temurin/releases/?version=21).
Choose the installer option that adds Java to PATH. Open a **new PowerShell** window:

```powershell
java -version
keytool -help
$SigningDir = Join-Path $env:USERPROFILE 'TiniumSigning'
New-Item -ItemType Directory -Force -Path $SigningDir | Out-Null
$DebugKeystore = Join-Path $SigningDir 'tinium-debug.keystore'
$ReleaseKeystore = Join-Path $SigningDir 'tinium-release.keystore'
```

Keep this folder outside any Git checkout. Use Windows device encryption/BitLocker
and a private Windows account. Do not store these files in a public/shared folder.
Nothing in this guide requires you to send passwords or keys to Codex chat.

## 2. Generate the persistent debug key once

Skip generation if you already have the debug key you want to preserve. These
credentials are **fixed** by the current project: alias `androiddebugkey`, store
password `android`, key password `android`. They are standard development values,
not credentials suitable for a permanent release key.

```powershell
if (Test-Path $DebugKeystore) { throw 'Debug keystore already exists. Reuse it; do not overwrite it.' }
keytool -genkeypair -storetype JKS -keystore "$DebugKeystore" `
  -storepass android -keypass android -alias androiddebugkey `
  -keyalg RSA -keysize 2048 -validity 10000 `
  -dname 'CN=Android Debug,O=Android,C=US'
if ($LASTEXITCODE -ne 0) { throw 'Debug key generation failed.' }
keytool -list -v -keystore "$DebugKeystore" -storepass android -alias androiddebugkey
```

Record the displayed **SHA256 certificate fingerprint**. Generate this key only
once, and keep using the same file for future development builds.

## 3. Generate the permanent release key once

**Only do this if you have never established a release identity for Tinium.**
Choose a stable alias (the example uses `tiniumrelease`) and long, unique passwords.
Use at least 12 characters; keytool requires at least 6. Avoid leading/trailing
whitespace. Save the alias and both passwords in your password manager. Use a
separate release key, never the debug key, even if you rename its alias.

The following command prompts privately for the keystore password and identity
fields, then for the key password. Passwords are not placed in PowerShell history:

```powershell
if (Test-Path $ReleaseKeystore) { throw 'Release keystore already exists. Reuse it; do not overwrite it.' }
$ReleaseAlias = 'tiniumrelease'  # You may choose another stable alias; do not use androiddebugkey.
keytool -genkeypair -storetype JKS -keystore "$ReleaseKeystore" `
  -alias "$ReleaseAlias" -keyalg RSA -keysize 4096 -validity 10000
if ($LASTEXITCODE -ne 0) { throw 'Release key generation failed.' }
keytool -list -v -keystore "$ReleaseKeystore" -alias "$ReleaseAlias"
```

Enter your chosen identity when prompted, not `CN=Android Debug`. At the key
password prompt, pressing Enter uses the store password for the key too. That is
supported; create **both** password secrets with the same value in that case. JKS
also supports different passwords if you prefer. Record this certificate's SHA256
fingerprint; it must differ from the debug certificate's fingerprint.

**Losing the release private key or its passwords can permanently prevent updates
to existing APK installations.** For direct APK distribution there is no automatic
Play App Signing recovery. Replacing the key normally forces users to uninstall,
losing app-local data unless they have an export/backup. GitHub Secrets are not a
backup you can later download.

## 4. Configure GitHub Actions repository secrets

In your browser open:

<https://github.com/yren411/vivi-music-personal/settings/secrets/actions>

Or navigate **repository → Settings → Secrets and variables → Actions → New
repository secret**. Use **repository secrets**, not Actions variables. You need
permission to manage the repository. Never paste these values into issues, PRs,
logs, source files, or chat.

Base64 is an encoding of the entire private keystore, **not encryption**, a file
path, or a SHA256 fingerprint. To avoid creating extra private Base64 files, copy
straight to the clipboard:

```powershell
Set-Clipboard -Value ([Convert]::ToBase64String([IO.File]::ReadAllBytes($DebugKeystore)))
```

Create `DEBUG_KEYSTORE_BASE64`, paste the clipboard in **Secret**, and save. Then:

```powershell
Set-Clipboard -Value ([Convert]::ToBase64String([IO.File]::ReadAllBytes($ReleaseKeystore)))
```

Create `ANDROID_SIGNING_KEY`, paste, and save. Create the remaining secrets manually
from the values you chose and saved in your password manager:

| Secret | Value |
| --- | --- |
| `DEBUG_KEYSTORE_BASE64` | Entire debug keystore encoded as Base64 |
| `ANDROID_SIGNING_KEY` | Entire permanent release keystore encoded as Base64 |
| `ANDROID_KEYSTORE_PASSWORD` | Password used to open the release keystore |
| `ANDROID_KEY_ALIAS` | Your release alias, e.g. `tiniumrelease` |
| `ANDROID_KEY_PASSWORD` | Password for the private key under that release alias |

You do **not** create an `ANDROID_KEYSTORE_PATH` secret. Workflows supply that path
inside the runner's temporary directory. Clear the clipboard after each paste:

```powershell
Set-Clipboard -Value ''
```

Also clear sensitive clipboard history (`Win+V`) if Windows has retained it, and
avoid clipboard synchronization while handling keys. Do not regenerate keys when
retrying a failed build: correct the secret names, Base64, alias, or passwords.
The workflows intentionally fail when signing secrets are missing.

## 5. Back up the keys before using them

Keep encrypted backups of **both** original binary keystores in at least two
independent locations, such as an encrypted offline USB drive and private encrypted
backup storage. Keep the passwords and aliases in a password manager. Record the
certificate fingerprints separately. Test that a restored backup opens with
`keytool -list -v`, and confirm its fingerprint matches the original. Restrict
who can edit secrets or trusted `main` workflow code; anyone able to run modified
trusted code with secrets can misuse a signing identity.

## 6. Trigger a development APK build

After merging the reviewed PR and adding `DEBUG_KEYSTORE_BASE64`:

1. Open **Actions → Build Tinium Development APK → Run workflow**.
2. Select `main` and click **Run workflow**.
3. Open the run; check that keystore validation and **Build ARM64 GMS Debug APK** succeed.
4. Download artifact **VIVI-Music-ARM64-GMS** (the existing artifact name is preserved).
5. Extract the ZIP and copy the APK to an ARM64 Android phone. Install it, allowing
   installation from that source if Android asks.

Runs on other refs skip trusted signing jobs. PR checks use disposable keys and do
not use the permanent debug or release keys. A push to `main` still triggers the
development workflow; before its secret is configured it will fail clearly.

## 7. Test release signing without publishing

After adding all four `ANDROID_*` release secrets:

1. Open **Actions → Beta Release Build → Run workflow**, select `main`, and run it.
2. Repeat with **Production Release Build**.
3. Both builds produce universal GMS and FOSS APKs in Actions artifacts, with the
   existing changelog JSON. The signature-check step must succeed for both APKs.
4. Compare the logged SHA256 fingerprints with your local release certificate:
   beta, production, GMS, and FOSS must all match. They must differ from debug.
5. Download artifacts and test privately. These workflows have `contents: read`
   permission and contain no public-release publishing step.

The current beta name remains `b6.0.8-r<workflow run number>`; production remains
`6.0.8`. No release key has been generated in Codex Cloud, and no build using your
permanent release key can be verified until you supply those secrets.

## 8. Verify APK signatures on Windows

For optional command-line checks, install Android Studio, then use **SDK Manager
→ SDK Tools** to install **Android SDK Build-Tools** and **Android SDK Platform-Tools**.
The default SDK directory is usually `$env:LOCALAPPDATA\Android\Sdk`.

```powershell
$AndroidSdk = Join-Path $env:LOCALAPPDATA 'Android\Sdk'
$BuildTools = Get-ChildItem (Join-Path $AndroidSdk 'build-tools') -Directory |
  Where-Object { $_.Name -match '^\d+\.\d+\.\d+$' } |
  Sort-Object { [version]$_.Name } -Descending | Select-Object -First 1
if (-not $BuildTools) { throw 'Install stable Android SDK Build-Tools first.' }
$ApkSigner = Join-Path $BuildTools.FullName 'apksigner.bat'
$ApkPath = Join-Path $env:USERPROFILE 'Downloads\app-arm64-gms-debug.apk' # Replace with your extracted APK path.
& $ApkSigner verify --verbose --print-certs "$ApkPath"
if ($LASTEXITCODE -ne 0) { throw 'APK signature verification failed.' }
```

Compare `Signer #1 certificate SHA-256 digest` with the local keystore SHA256
fingerprint (ignore colons and letter case). Verify both beta and production APKs
with this command, using the paths you extracted.

## 9. Test update compatibility

All existing flavors/build types keep **`com.yren411.tinium`**: there is no debug,
beta, GMS, FOSS, or ABI application-ID suffix. Namespace and source packages remain
`com.music.vivi`. Tinium retains its separate identity from original VIVI Music.

| Transition | Requirement / outcome |
| --- | --- |
| Persistent debug → next persistent debug | Same debug certificate; compatible version code; updates without uninstalling |
| Release → next release | Same permanent release certificate; compatible version code |
| Beta ↔ production | Same app ID and release certificate; destination version code must not be lower |
| GMS ↔ FOSS / ABI flavors | Same package; compatible certificate, version code, and device architecture; replaces installed Tinium |
| Debug ↔ release | Different certificates; cannot update or coexist under this shared app ID; normally requires uninstalling |
| Old temporary debug → persistent debug | Different certificate; normally requires uninstalling old Tinium first |

Export/backup your app data before uninstalling. A new persistent debug key cannot
update an old APK signed by an unrelated temporary debug key.

The current `versionCode` is **77** for all these variants. Beta's changing
`versionName` does **not** increase the version code. Android normally permits
same-code reinstalls with the same certificate, but use strictly increasing
version codes for future distributed updates; some installers/distribution
channels require an increase. Installing a lower code is a downgrade and normally
fails. This change deliberately leaves versioning unchanged. A beta with a higher
code will prevent returning to an older production code without uninstalling.

For a practical test, install the first persistent-debug APK, add a playlist or
other harmless local state, run another development build using the same key,
and install it over the first. Verify Android offers an update and the state
remains. Repeat privately with beta and production signed by the release key.

With USB debugging enabled on a connected Android phone, an optional exact check is:

```powershell
$Adb = Join-Path $AndroidSdk 'platform-tools\adb.exe'
& $Adb devices
& $Adb install -r "$ApkPath"
```

`INSTALL_FAILED_UPDATE_INCOMPATIBLE` usually means a certificate mismatch.
`INSTALL_FAILED_VERSION_DOWNGRADE` means the destination version code is lower.
Do not use downgrade flags to mask an incompatible release/versioning plan.

## Local release builds (optional)

Local release builds must point to your existing keystore outside the checkout via
`ANDROID_KEYSTORE_PATH`, with `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, and
`ANDROID_KEY_PASSWORD` in the process environment. Do not write credentials to
`local.properties`, Gradle files, or shell history. A base64 `ANDROID_SIGNING_KEY`
is a CI restoration input; Gradle itself reads the decoded file. Without those
four environment values, release packaging fails rather than signing with debug.
Do not change or remove an old keystore until its fingerprint has been compared
with previously distributed APKs.
